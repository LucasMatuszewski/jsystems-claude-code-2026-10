# Code-graph tools vs repo maps for legacy Java (research and jFTP trial, 14.10.2026)

## Recommendation

Use our `legacy-codebase-workflows` skill as the course default: direct `rg` for a known symbol, a scoped `legacy-repo-map` for an unfamiliar area, then original method bodies or a selected full-code Repomix pack. Add **codebase-memory-mcp (CBM)** when repeated caller and change-impact questions cross files. Keep **Graphify** as an optional code-only graph exploration exercise. Neither graph is an authority for deleting code or changing a Java API without checking source and tests.

For corporate Java projects that already import correctly in Eclipse or IntelliJ, use the IDE's resolved references first; evaluate **Serena with Eclipse JDT LS** when agents need that semantic navigation. For projects that cannot build or import, CBM is the first graph pilot because it runs without the JVM toolchain. Document this optional integration in our skill; do not replace its mapper, evidence checks or refactoring workflow.

Research date: 2026-10-14. Labels: **[measured]** = this jFTP trial; **[official]** = upstream documentation/source; **[research]** = paper/preprint; **[vendor claim]** = producer-run result; **[community]** = public discussion or issue report, not independent validation. UNCONFIRMED identifies an untested or unresolved claim. Popularity is a selection signal, not a quality score.

## Hands-on results on jFTP

### Method and limits

Cloned public [sai-pullabhotla/jftp](https://github.com/sai-pullabhotla/jftp) into a fresh temporary directory, revision `14e62ceba4e371c2a0b955604b10f065f46f4f7d`: 182 Java files and 29,330 Java source lines. Environment: Linux x86-64, Ubuntu 26.04/WSL2, Python 3.14.4. This is a navigation trial on a small legacy application, not validation on a corporate monorepo, a Windows installation test or an application runtime test.

Setup downloads were online. Offline runs used a Linux seccomp wrapper that denied creation of IPv4 and IPv6 sockets while allowing Unix-domain IPC; its self-test passed. CBM was also indexed from an empty separate cache under that filter. Graphify used `--code-only`, cached dependencies, `uvx --offline`, and a forced fresh extraction; clustering used `--no-label --no-viz`. No source was sent to a cloud LLM. Source remained unchanged. No agent client installer or configuration registration was invoked.

Times are individual subprocess wall-clock observations, not medians or a speed benchmark. Filesystem caches were not flushed. Size estimates use `ceil(Unicode characters / 4)`, not model tokenization or billed tokens. A disk graph and a prompt response are deliberately listed separately.

| Tool | Setup and wall time | Fresh build/index | Output and estimated tokens | Offline result |
|---|---|---|---|---|
| `legacy-repo-map` 0.3.0 | `status` -> needs setup; pinned `install` failed in 0.39 s; explicit successful CI install took 6.30 s | 0.39 s at default 16,384 estimated-token budget; 182 parsed files, 1,586 captured definitions, 1,019 selected, 567 omitted | Raw map 65,530 characters / 16,383 estimates; exported report 67,027 / 16,757 including headers | Passed network-denied mapping; no daemon |
| CBM 0.11.0 | Official linux-amd64 archive + checksums downloaded in 0.94 s; SHA-256 matched; no install script | Initial online-capable local run 9.63 s; fresh network-denied run 14.28 s; initial 5,878 nodes / 17,440 edges, fresh offline 5,850 / 17,412 | Initial SQLite index 17,956,864 bytes (fresh offline 17,891,328); four core responses 10,106 characters / 2,527 estimates; all nine exploratory/follow-up responses 32,334 / 8,084 | Fresh indexing and queries passed; temporary coordination daemons stopped after CLI sessions |
| Graphify 0.9.91 | `uvx --from graphifyy graphify --help`, resolved package/dependencies in 1.66 s | Initial code-only extraction 5.51 s; forced network-denied extraction 4.32 s; 2,249 nodes / 7,299 edges, 118 communities | Graph JSON 3,469,042 characters / 867,261 estimates on disk; seven query responses 5,815 / 1,454; report 9,955 / 2,489 | Code extraction, queries and unlabeled clustering passed; no daemon |

**Setup blocker [measured]:** the mapper's normal installer returned `pinned release is not published or this asset is missing`. Authenticated GitHub lookup of `legacy-tools-v0.3.0` also returned HTTP 404. The documented CI route succeeded with run `38201257075`, source `583c9a32b930f1fa8fbbc4ff4010e6acb5f0471d`. Prepare and verify the course binaries before class; the claimed default release-install path is not currently demonstrated. This finding is not a reason to silently substitute another version.

**Coverage [measured]:** initial CBM indexing reported three partially parsed help HTML files, one unusably parsed shell script and 97 intentionally unindexed files. The fresh offline run additionally reported `parse timeout` for `HelpMenu_de.properties`, and had 28 fewer nodes/edges. This is a partial extraction warning despite overall status `indexed`, not evidence that network denial caused the timeout. No Java parse failure was reported; graphs were not assumed identical. Graphify classified 184 code files but skipped non-code resources; four yielded no symbols, including `pom.xml` and three `package-info.java` files. Properties/configuration wiring therefore still needs source inspection. Its graph contained 6,478 EXTRACTED and 821 INFERRED edges, even in code-only mode. INFERRED does not necessarily mean LLM-generated.

### Five common questions and source checks

Answers were first recorded from tool outputs, then checked against source with `rg`. For impact, the explicitly selected API is `FTPSession.connect(RemoteHost)`, not every method of the class. For callers, distinguish calls to that in-repository entry from the lower-level FTP library's `connect/login` calls. We did not build or index the external FTP dependency. Correct = sufficient for the stated bounded question; partial = useful evidence with a material gap; wrong = contradicted by source; not supported = no adequate answer. These are manual judgments, not an automated answer-quality benchmark.

| Question | Default map only | CBM output only | Graphify output only | Source verification |
|---|---|---|---|---|
| (a) Which classes call connection/login logic? | **Not supported:** shows `FTPSession`, `getFTPClient`, `reconnect`, but omits `connect` and caller relationships | **Partial:** correctly finds `ConnectAction`, `FavoritesDlg`, `FTPSession.reconnect`; does not establish lower-level login body | **Partial:** same correct entry-point callers; graph has no `login` node | `ConnectAction.java:73`, `FavoritesDlg.java:249`, `FTPSession.java:703`; library calls are inside the session's worker at `FTPSession.java:649-652` |
| (b) Impact of changing `FTPSession.connect` signature? | **Not supported:** a declaration map cannot enumerate callers; this declaration was also omitted | **Correct, bounded:** the three direct callers, plus `ReconnectAction` and Favorites dialog handlers transitively; filter pseudo-file edges | **Correct, bounded:** `affected` returned the same direct callers and transitive handlers | Direct call sites above; `ReconnectAction.java:55`, `FavoritesDlg.java:101,142`; not a guarantee about reflection/external consumers |
| (c) GUI start and main-window wiring? | **Partial:** identifies `JFTP extends MFrame` and `JFTPApplication`, but omits `main` and constructors | **Correct for core answer:** `JFTPApplication.main` -> constructor -> `JFTP`/`newSession`; additional low-confidence edges are wrong | **Partial:** finds `main` -> application constructor and a class reference to `JFTP`; omits the constructor's actual `new JFTP()` edge | `JFTPApplication.java:55,61-66`; manifest main class in `pom.xml:122` |
| (d) Dead or unused classes? | **Not supported:** absence from a budgeted map is not evidence of unused code | **Partial candidate discovery:** degree-zero search finds real leads but also demonstrably live classes; a blanket dead-class answer would be **wrong** | **Not supported:** `query "dead unused classes"` returned no matching nodes; no dead-code conclusion from the tested surface | `Encoder`/`StringUtilities` had no references outside their own files in the searched Java/XML/HTML/properties scope; CBM also listed live `ImageCellRenderer`, `ThreadVar` and transferables |
| (e) Compact architecture overview? | **Correct as a structural sketch:** application/session, GUI widgets, actions, SSL and utility declarations with original paths | **Partial:** identifies hotspots/session coupling, but package groups `main`/`pom`/`project` and clusters named `src` provide weak architecture | **Correct as a structural sketch:** hubs `JFTP`, `FTPSession`, `LocalFile`, preferences and GUI classes, plus paths; communities remain unlabeled | Package/source inspection confirms roles; behavioral and dependency details require bodies, resources and `pom.xml` |

**Useful graph result [measured]:** Graphify returned `ConnectAction.java:L73`, `FavoritesDlg.java:L249` and `FTPSession.java:L703` for the connection entry. CBM reported the same method callers with resolver/confidence fields, plus an extra `__file__` caller at confidence 0.04. That synthetic file relationship must not be presented as a fourth Java caller.

**Concrete wrong edges [measured]:** CBM's constructor trace points `setVisible` to `SplashWindow.setVisible` and `getLookAndFeelClassName` to `UIPrefsPanel.getLookAndFeelClassName`, both at confidence 0.28. Source actually calls `jftp.setVisible(true)` and `JFTP.prefs.getLookAndFeelClassName()`. The splash code is commented out. Its dead-class list also includes `ImageCellRenderer`, actively constructed in `FavoritesDlg.java:267` and `PreferencesDlg.java:172`; nested `ThreadVar` is constructed in `SwingWorker.java:146`, and transferables in `DnDTransferHandler.java:78,81`. Degree-zero is not equivalent to unused Java code.

**Dependency boundary [measured]:** `FTPSession.java:624-627` instantiates FTP client/parser classes through `Class.forName`; actual network connect/login is inside an anonymous worker. Graph navigation finds the session entry quickly but neither tested graph establishes the absent library's implementation or complete runtime dispatch. Verify that boundary separately before changing the library API.

**Token interpretation [measured]:** the graph responses were smaller than loading the whole default map, but answered narrower questions and required symbol discovery/follow-ups. CBM's nine responses took about 5.3-5.6 s each in this one-shot CLI setup; Graphify's seven took 0.43-0.61 s each. Persistent MCP latency was not tested. Loading Graphify's entire JSON would be far larger than the map. No 10x/99% savings or end-to-end task-cost claim follows from these observations.

## Benefits, costs and place in the workflow

### Our skill

**Strengths:** explicit output budget, inventory/coverage and omission accounting, export sidecars, source hashes/ranges and a separate citation checker; native mapping needs no daemon or LLM. The workflow combines navigation with bodies/configuration, characterization tests and independent verification. Optional private retrieval rejects stale sources; changing the vector database cannot fix unsuitable representations or missing candidates, as [ADR 000](https://github.com/EdukeyTeam/agent-toolbox/blob/main/docs/ADR/000-local-code-retrieval-storage.md) explains.

**Limits:** our Java map is syntactic; identifier ranking cannot disambiguate overloads or provide a caller query. Default selection omitted important entry points on jFTP. Native mapping regenerates rather than incrementally maintaining a queryable graph. The small trial and existing limits do not establish production-scale readiness.

**Large single files:** open [PR 18](https://github.com/EdukeyTeam/agent-toolbox/pull/18) proposes a Java member outline/slice tool and baseline/compare ledger. It tracks unchanged, moved, signature-changed, modified and missing members, addressing incomplete refactors of 5,000-line files. It is not merged and is not in the tested 0.3.0 binary. Its reported corpus tests were reviewed as PR evidence, not rerun here. A graph adds cross-file navigation; it does not replace member accounting or behavior tests.

### codebase-memory-mcp

**Benefits:** convenient bounded caller/impact queries, queryable persistent index and source/strategy/confidence fields. It adds useful navigation beyond our static map without requiring a working Java build. The verified release provides a direct binary path without registering client hooks.

**Costs:** own resolver and heuristics can invent relationships; dead-code candidates require verification. CLI invocations participated in shared daemon lifecycle, and the initial default attempted a local UI. Map-style citation evidence still has to be captured against current source. Upstream documents incremental refresh during active MCP sessions; one-shot CLI indexing is not a continuously fresh index. Incremental refresh and persistent MCP performance were not tested here.

**Decision:** first optional graph pilot, with an explicit index-coverage gate. Use the exact qualified symbol, a narrow depth/result budget, evidence/confidence and source verification. Keep client auto-installation and hooks out of the course demo.

### Graphify

**Benefits:** code-only setup worked, caller/impact responses were readable and small, and relationships retain confidence tags and locations. It offers graph reports and visualization without a graph database server. Graph queries can complement our overview with explicit connections.

**Costs:** the real graph is much larger than its query results; a visual cluster is not necessarily a subsystem. Constructor and external-library gaps matter for Java. Code-only excludes resources, semantic extraction/labeling are distinct features, and inferred relationships also come from deterministic resolution. Upstream supports `update`/`watch`; freshness behavior was not tested. The HTML visualization was not generated or visually assessed in this trial.

**Decision:** optional teaching/demo alternative, especially for graph inspection; not the primary corporate Java impact tool based on this trial.

### Other serious options

**Serena:** a stronger semantic-navigation candidate when JDT LS can import the real project. It adds symbol retrieval/editing rather than a general graph DB. Setup can fail on an unavailable JDK, unsupported legacy build or missing dependency sources; test import before promising precision. Its current component licence is known from the actual LICENSE file, despite GitHub reporting NOASSERTION. No hands-on Serena result is claimed.

**code-graph-rag / CodeGraphContext:** reasonable pilots where graph storage or compiler/tracing integration is specifically needed. Their infrastructure and backend choices add operational cost; documentation alone does not establish better Java answers than CBM. Do not assume CodeGraphContext's optional SCIP means it runs SCIP-Java.

**SCIP-based options:** best considered when the company already has compiler-produced references and a consumer. A precise index requires the right build/classpath and freshness; it cannot manufacture a compilable environment. **GitNexus:** its actual noncommercial licence prevents treating it as an unrestricted corporate default; obtain suitable permission before adoption.

## Evidence of benefit

**[Research, independent structural-index study]** Bhola et al., [Code Isn't Memory](https://arxiv.org/abs/2606.22417), evaluates index/no-index and agentic-grep arms in a fixed harness/model on SWE-PolyBench Verified and SWE-bench Pro, across three seeds. The abstract reports improved localization and resolve, no cost penalty per cell and lower cost per solve. This supports testing structural indexes for multi-file work, not choosing CBM over Graphify. Exact effect sizes and reproduction are UNCONFIRMED here.

**[Research, tool-specific evaluation]** Vogel et al., [Codebase-Memory](https://arxiv.org/abs/2603.27277), reports 31 repositories, 10x fewer tokens and 2.1x fewer tool calls, but 83% answer quality versus 92% with file exploration. It matches or exceeds exploration on graph-native queries in 19/31 languages. Keep both the savings and the quality trade-off; this is not a neutral current-release Java comparison.

**[Vendor claims]** CBM's README reports roughly 120x token savings for its own five-query comparison; Graphify's [BENCHMARKS.md](https://github.com/Graphify-Labs/graphify/blob/v8/BENCHMARKS.md) reports ERPNext key-fact coverage of 82.0% versus a 70.8% grep/read baseline over six code questions. Its LOCOMO recall@10 0.497 and LongMemEval-S 76% address conversational memory, not Java impact correctness. Repomix compression and CodeGraphContext's compact formats likewise measure representation size, not safety or task success. None was reproduced here.

**[Community]** The [Graphify C# HN thread](https://news.ycombinator.com/item?id=49667188) had 46 points/20 comments when fetched; its compiler-accurate positioning illustrates demand for more precise references but is a creator announcement, not a Java benchmark. Current reports include [CBM Windows indexing failure on a file named nul](https://github.com/DeusData/codebase-memory-mcp/issues/2646), [Graphify fabricated callback-call edges](https://github.com/Graphify-Labs/graphify/issues/4448) and [Graphify skill-shell quoting trouble](https://github.com/Graphify-Labs/graphify/issues/4461). These are unverified reporter claims relevant to rollout testing. No X-post evidence was used.

## Adoption risks and exact proposed skill change

Keep private source and generated indexes inside the company's approved boundary. A local index does not make a hosted coding-agent conversation local: returned code excerpts may still enter that agent's context. Separate offline code extraction from optional remote labeling, chat, embedding downloads and hosted services. Test unsigned binaries, Python/uv/JDK provisioning and endpoint protection on a representative corporate Windows laptop before class; this Linux run proves none of those policies permit execution.

Freshness, generated code, overloaded names, listeners, reflection, XML/properties wiring and absent dependency sources are coverage risks. Treat dead-code findings as leads. Check the source and tests before deletion, API edits or a refactor. Do not interpret confidence numbers as measured probabilities of correctness. Keep setup versions and source revisions with results.

**Proposed change, not applied:** add `references/code-graphs.md` to the skill and a single workflow-table link from `SKILL.md`: `Repeated cross-file callers or impact questions | Optional local code graph, then original source`. The reference should document CBM as the first pilot, Graphify code-only as an alternative, and JDT LS/SCIP when compiler inputs exist. Include pinned direct-binary setup without client registration, an isolated cache, `index_repository` -> exact `search_graph` -> inbound `trace_path` with evidence -> source read, bounded response limits, refresh/cleanup and the five-question jFTP acceptance exercise. Require rejecting pseudo-file callers and checking known false-positive dead-code examples. Preserve map/export/citation checks and the proposed member ledger as separate capabilities; add no automatic daemon, hook or MCP dependency.
