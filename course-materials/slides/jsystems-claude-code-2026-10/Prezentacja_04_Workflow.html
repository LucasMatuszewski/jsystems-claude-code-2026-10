Skills

Skills w praktyce

  • Instalujemy skills z publicznego repozytorium EdukeyTeam i porównujemy dwie metody instalacji.
  • Skill do systemu wizualnego: agent czyta instrukcję, używa narzędzi i przygotowuje pliki do przeglądu.
  • Przy PRD skill dostarcza metodę, a prompt tylko opis naszej aplikacji.
Model pracy

Dwie pętle: budowa i weryfikacja

  1. Poproś o rozpoznanie i plan bez edycji.
  2. Zatwierdź mały zakres.
  3. Agent edytuje i pokazuje diff.
  4. Uruchom testy oraz ocenę ręczną.
  5. Zapisz decyzję i następny krok.

Jeśli test nie przechodzi, wróć do obserwacji. Nie maskuj błędu zmianą testu bez uzasadnienia.

Agenci / repozytorium

Instrukcje repozytorium dla agenta

Stałe fakty

Cel projektu, mapa plików, komendy testów potwierdzone na starterze.

Granice

Nie edytuj testów tylko po to, by były zielone. Nie umieszczaj sekretów ani danych klientów.

Weryfikacja

Po zmianie pokaż diff, wynik testów i jedną rzecz nadal niepewną.

Moduł 1.3

CLAUDE.md i AGENTS.md - pamięć agenta

CLAUDE.md

Plik instrukcji dla Claude Code. Agent wczytuje go automatycznie przy starcie.

Poziomy:

  • ./CLAUDE.md - poziom projektu
  • ~/.claude/CLAUDE.md - poziom globalny

AGENTS.md

Wspólny, otwarty standard dla wielu agentów: Codex, OpenCode, Antigravity, Cursor i inne.

Claude Code nie czyta go automatycznie - ale wystarczy zaimportować go w CLAUDE.md (jak załącznik w mailu):

# CLAUDE.md @AGENTS.md ## Instrukcje tylko dla Claude Code - Role be-developer / fe-developer / qa-engineer definiujemy w module 2.3

Jedno źródło prawdy w AGENTS.md, zero duplikacji - dokładnie tak jest skonfigurowane repo kursowe.

Co zawierają: konwencje kodu, opis stacku, zasady nazewnictwa, strukturę projektu, wytyczne testowe, rzeczy których agent ma unikać.
Moduł 1.3

Struktura kontekstu agenta

Co składa się na to, co agent "wie" w danej chwili

1. System prompt

Wbudowane instrukcje od dostawcy. Definiują zachowanie bazowe agenta.

2. Konfiguracja

Model, uprawnienia (permissions.allow / permissions.deny), tryb bezpieczeństwa.

3. CLAUDE.md / AGENTS.md

Trwała pamięć agenta. Konwencje, zasady, opis projektu.

4. Historia sesji

Przebieg bieżącej rozmowy. Kompresowana przez /compact.

5. Aktywne pliki

Pliki otwarte, wzmiankowane lub edytowane w bieżącej sesji.

= Kontekst agenta

Suma wszystkich powyższych. Im lepszy kontekst, tym lepsze wyniki.

Użyj /context, aby zobaczyć aktualny stan kontekstu swojego agenta.
Moduł 1.3

Path-based rules vs nested CLAUDE.md

Nested CLAUDE.md

Pliki CLAUDE.md w podkatalogach projektu.

Gdy agent wchodzi do katalogu, czyta tamtejszy CLAUDE.md.

projekt/ CLAUDE.md # globalne reguły frontend/ CLAUDE.md # reguły dla FE backend/ CLAUDE.md # reguły dla BE

Path-based rules

Reguły to pliki Markdown w .claude/rules/ z polem paths: we frontmatter.

# .claude/rules/frontend.md --- paths: - "frontend/**/*" --- Używaj komponentów funkcyjnych React.
Wybór: nested dla dużych projektów z wyraźnymi modułami. Path-based dla mniejszych projektów z specyficznymi regułami per katalog.
Moduł 1.3

Best practices: jak pisać CLAUDE.md

Krótko i konkretnie

Celuj w około 200 linii jako zalecenie kursowe, nie limit techniczny. Pełny CLAUDE.md jest ładowany niezależnie od długości.

Konkretne reguły

Źle: "Pisz czysty kod". Dobrze: "Używaj TypeScript strict mode, wszystkie funkcje muszą mieć typy zwracane."

Iteruj

Dodaj regułę za każdym razem, gdy agent popełni błąd. CLAUDE.md to żywy dokument.

Wersjonuj w git

CLAUDE.md w repozytorium = cała drużyna ma te same reguły. Historia zmian widoczna.

# CLAUDE.md - przykład ## Stack TypeScript, React, Vercel AI SDK; decyzje w ADR ## Konwencje - Używaj TypeScript strict mode - Komponenty funkcyjne, nie class components - Nazwy plików: kebab-case ## Testy - Testy PRZED implementacją (TDD) - Unit: mocki zależności; integracja: mock tylko zewnętrznego LLM; E2E: realny stos
Skills / ćwiczenie

Zainstaluj publiczne skills ręcznie

W katalogu projektu sprawdź listę w publicznym repozytorium:

npx --yes skills@latest add EdukeyTeam/agent-toolbox --list

Zweryfikowane nazwy w źródle: write-prd i write-adr. Potem wybierz jedną:

npx --yes skills@latest add EdukeyTeam/agent-toolbox --skill write-prd --agent claude-code
npx --yes skills@latest add EdukeyTeam/agent-toolbox --skill write-adr --agent claude-code

Instalacja do projektu jest domyślna. Jeśli CLI pyta o miejsce, wybierz projekt. Sprawdź, czy Claude Code widzi skill w .claude/skills/. Instalator może tworzyć tam symlink do wspólnej kopii w .agents/skills/; sprawdź także skills-lock.json. Nie kopiuj folderu ręcznie.

Zasady repo / pełny prompt

Kontrakt jakości z agentem

Zasady repozytorium i jakości

Skopiuj prompt poniżej lub otwórz go jako plik Markdown albo w bibliotece promptów.

Sprawdź to repozytorium i zaproponuj zwięzłe instrukcje projektowe dla Claude Code. Ustalaj tylko reguły uzasadnione rzeczywistym szkieletem AI Chat; nie przenoś języka, runnera testów, menedżera pakietów, ścieżek ustawień ani składni innego narzędzia bez sprawdzenia. TypeScript, Vercel AI SDK, React useChat i streaming są ramami kursu, a szczegóły architektury wynikają z ADR.

Jeśli istnieje `course-materials/`, traktuj go jako nieaktywną bibliotekę dydaktyczną. Agent aplikacji nie może sam jej przeszukiwać ani odczytywać, chyba że użytkownik wskaże konkretny materiał do bieżącego zadania. Przykładowe PRD i ADR nie są wymaganiami ani decyzjami tej aplikacji. Zapisz tę granicę w głównych instrukcjach oraz aktywnym pliku dla narzędzia, zachowując możliwość jawnie zleconej pracy nad materiałami.

Najpierw opisz faktyczną strukturę repozytorium i sprawdzone polecenia. Wskaż, które dokumenty zawierają wymagania produktu, decyzje architektoniczne, polityki, testy i syntetyczne dane. Rozróżnij dokumenty już istniejące od wyników przyszłych ćwiczeń. Wskaż katalogi generowane, sekrety i dane, które nie mogą trafić do Git. Jeśli polecenie nie działa w tym środowisku, przytocz dokładny błąd i nie przedstawiaj go jako sprawdzonego.

Zaproponuj krótkie instrukcje obejmujące:

1. Cel AI Chat, dokumenty rozstrzygające zachowanie i granice kodu aplikacji względem materiałów kursowych. Gdy PRD lub ADR nie powstały, wskaż tę zależność zamiast je zastępować.
2. Polecenia szybkiego testu, pełnej weryfikacji, lint/typecheck i uruchomienia aplikacji, wyłącznie na podstawie tego projektu. Nie wymyślaj nazw skryptów ani gotowego wyniku.
3. Zakres zadania: istotne źródła, mały plan, jedno kryterium akceptacji, przegląd diffu. Bramka przed commitem wymaga właściwych testów i kontroli typów, właściwych plików oraz rozwiązania błędów. Staging obejmuje jawne ścieżki; bez `git add -A`, `git add .` i `git commit -a`.
4. Testowanie zachowania według specyfikacji: najpierw test, jego oczekiwana porażka, minimalna implementacja, ponowny test i refaktoryzacja przy zielonej weryfikacji. Osobno zapisuj uruchomienie aplikacji oraz kontrolę UI/API. Nie osłabiaj asercji, aby ukryć defekt.
5. Wywołania modelu: unit może zastępować zależności, integration zastępuje tylko zewnętrzny LLM, E2E działa na rzeczywistym stosie. Przed utworzeniem mocka uzyskaj bezpieczny capture aktualnego kontraktu w autoryzowanym środowisku. Nie ujawniaj wartości sekretów ani danych uczestników i klientów.
6. Warunki zatrzymujące ukończenie: nieprzechodzące wymagane testy, nieprzejrzany diff, niesprawdzone twierdzenie, pliki prywatne lub wygenerowane, zmiana poza przyjętym zakresem. Agent zgłasza dokładny brak zamiast uznać zadanie za zakończone.

Jeżeli frontend i backend mają rzeczywiście odmienne konwencje lub polecenia, zaproponuj niewielkie instrukcje lokalne. Wspólne reguły zachowaj w AGENTS.md, a w CLAUDE.md użyj jawnego importu `@AGENTS.md`. Claude Code nie ładuje automatycznie samego AGENTS.md jako pamięci. Dla reguł ścieżek porównaj `.claude/rules/*.md` z `paths` i zagnieżdżony CLAUDE.md; nie kopiuj bez namysłu przepisu na symlink z innego narzędzia.

Kontekst AI Chat: kontrakt endpointu i streamingu ustalamy przed równoległą pracą. Role to `be-developer`, `fe-developer` oraz `qa-engineer`; uczestnik definiuje je w module 2.3. Przykłady w `course-materials/agent-configs/claude/` są nieaktywne. Wskaż właściciela wspólnego kontraktu i lockfile. QA może przygotować scenariusze równolegle, lecz E2E uruchamia po integracji. Nie zakładaj autoryzacji ani bazy historii, jeśli PRD ich nie wymaga.

Zwróć pełną proponowaną treść plików, sprawdzone polecenia i wyniki oraz przykład zadania uruchamiającego bramkę jakości. Nie zmieniaj ustawień globalnych i nie instaluj narzędzi w ramach tego zadania. Wyjaśnij każdą regułę, dla której nie znalazłeś źródła, zamiast przedstawiać preferencję jako fakt projektu.
Repozytorium

Agent potrzebuje granic zadania

  • Podaj punkt wejścia, testy, definicję gotowości i pliki poza zakresem.
  • Zacznij od odczytu statusu oraz struktury repozytorium; nie od masowej edycji.
  • Zapytaj o plan, potem pozwól zmieniać mały zakres.
  • Po każdym kroku czytaj diff i uruchom właściwe testy.
04 / implementacja

Mały fragment, test przed kodem

  • Wybierz jedną funkcję z PRD i ustal mierzalne kryterium zaliczenia.
  • Agent dodaje lub uruchamia test, który ujawnia brak zachowania - nie zmieniaj asercji, żeby uzyskać pozorny zielony wynik.
  • Agent wdraża najmniejszą potrzebną zmianę i uruchamia testy fragmentu, a potem testy całości.
  • Ty ustalasz zakres, przeglądasz diff, sprawdzasz zgodność z ADR i zatwierdzasz wynik.

Czym jest MCP

MCP łączy agenta z zewnętrznymi narzędziami.

Jak działa

  • Serwer udostępnia narzędzia; agent wywołuje je, gdy są potrzebne.

Moduł 2.1 / ważny trend

CLI i MCP: koszty oraz korzyści

MCP

  • Gotowa integracja udostępnia agentowi narzędzia.
  • Wymaga konfiguracji i kontroli dostępu.

CLI

  • Agent uruchamia polecenie, gdy jest potrzebne.
  • Łatwo sprawdzić wejście, wyjście i błędy.
Coraz częściej wybieramy CLI: mniej tokenów w kontekście i prostsze debugowanie. MCP zostaje tam, gdzie nie ma dobrego CLI.
Moduł 2.1 | Ważny trend

CLI rośnie vs MCP

Klasycznie: serwer MCP stale włączony

  • Lokalny serwer stdio może pozostawać uruchomiony przez sesję; zdalny HTTP działa poza VM
  • Narzut zależy od transportu, serwera, liczby narzędzi i sposobu ich ładowania

Trend: CLI wywoływane przez agenta

  • Agent wywołuje narzędzie CLI na żądanie, gdy potrzebuje
  • Brak stale działającego serwera - mniej narzutu
  • Narzędzie startuje, robi robotę, kończy
  • Łatwiejsze debugowanie i izolacja
Praktyczna konsekwencja: coraz więcej narzędzi dostępnych jako CLI wywoływane przez agenta, zamiast trwale skonfigurowanego serwera MCP. Wybieraj świadomie - MCP dla stałych integracji, CLI/Skills dla jednorazowych i workflow.
Moduł 2.1

Dlaczego coraz częściej Skills zamiast MCP

MCP - kiedy jeszcze sensowne

  • Stała integracja z usługą (baza danych, API)
  • Narzędzie, którego używasz codziennie, przez cały projekt
  • Playwright MCP - sterowanie przeglądarką w E2E
  • Context7 - dokumentacja na żądanie

Skills - kiedy lepsze

  • Powtarzalny workflow (ciąg kroków, nie jedno narzędzie)
  • Bundle instrukcji + skryptów w jednym miejscu
  • Łatwiejsze do wersjonowania i udostępniania
  • Mniej narzut niż utrzymywanie serwera MCP
Trend: agenty przechodzą od "stałych serwerów MCP" do "Skills + CLI wywoływane na żądanie". Skill opisuje workflow i może wywoływać CLI albo MCP. Dobierz mechanizm do zadania i sprawdź rzeczywisty narzut.
2.1 / konfiguracja

MCP na Linuxie: .mcp.json i zaufanie

{"mcpServers":{"context7":{"type":"http","url":"https://mcp.context7.com/mcp"},"playwright":{"command":"npx","args":["-y","@playwright/mcp@latest","--browser","chrome"]}}}
  • Projektowe serwery zapisujemy w .mcp.json; lokalny i użytkownika zakres konfigurujemy przez claude mcp.
  • Wpisz /mcp, sprawdź status i zakres. Zaakceptuj tylko zaufany serwer; jego opis i wyniki także mogą zawierać niezaufaną treść.
  • Na Ubuntu uruchamiamy npx bez Windowsowego cmd /c. Context7 w dostępie publicznym ma limity; klucze przechowuj lokalnie.
  • Przykłady innych serwerów: GitHub, filesystem i własne API. Ogranicz dostęp do repozytorium i danych testowych.

Moduł 2.1 | Narzędzia

Context7 - aktualna dokumentacja

Co to jest

  • Serwer MCP dostarczający aktualną dokumentację bibliotek
  • Agent pobiera dokumentację na żądanie, gdy pisze kod
  • Ogranicza ryzyko użycia nieaktualnego lub wymyślonego API; wynik nadal trzeba zweryfikować
  • Działa dla dowolnej biblioteki z indeksem Context7

Dlaczego ważne

Bez Context7 agent opiera się na wiedzy z treningu, która może być nieaktualna. Z Context7 agent ma dostęp do realnej, bieżącej dokumentacji.

Idealne dla naszego projektu: dokumentacja Vercel AI SDK, React, TypeScript - wszystko aktualne.

Praktyka: gdy agent pisze kod z biblioteką, poproś go o sprawdzenie dokumentacji przez Context7.
Moduł 2.1 | Narzędzia

Playwright MCP - przeglądarka w rękach agenta

Sterowanie przeglądarką

Agent otwiera strony, klika, czyta DOM, robi zrzuty ekranu. Pełna automatyzacja przeglądarki przez MCP.

Design Guidelines

Reverse-engineering designu dowolnej strony: kolory, typografia, układy. Wyciąganie design tokens do własnej aplikacji.

Testy E2E

Automatyczne testy end-to-end. Agent wchodzi na aplikację, klika, weryfikuje czy funkcja działa. Bez mockowania.

Manualne testy agenta

Agent testuje aplikację jak człowiek: otwiera, przechodzi przez flow i sprawdza rezultaty. W E2E używa realnego stosu, w tym prawdziwego LLM.

W naszym procesie: Playwright MCP jest kluczowe na dwóch etapach - Design Guidelines (RAZEM 2.1) oraz testy manualne aplikacji.

Moduł 2.2

Własne komendy i Skills

Custom slash commands zostały scalone ze skills - oba tworzą /x

Prosta komenda Markdown

  • .claude/commands/x.md tworzy komendę /x
  • To samo co .claude/skills/x/SKILL.md - oba tworzą /x
  • Świadome, jawne wywołanie /nazwa
  • Wspiera $ARGUMENTS (wstrzykiwanie argumentu)
  • Grupowanie w podfolderach tworzy namespace
Przykład: .claude/commands/git/commit.md wywołuje się jako /git:commit. Drugi przykład: .claude/commands/git/diff.md - /git:diff.

Skill z dodatkowymi plikami

  • Katalog .claude/skills/x/ z SKILL.md + skryptami
  • Agent sam dobiera skill z pola description
  • Auto-trigger kontekstowy (heurystyka opisu)
  • Dołącza skrypty, assets i referencje
  • Metadane określające, kiedy się aktywuje
Kiedy skill wielo-plikowy: gdy agent ma SAM wykryć kontekst, gdy wiedza wymaga wielu plików, gdy potrzebne są dołączone skrypty i assets.
Reguła: prosty, jednokrotny prompt = jeden plik Markdown wywoływany świadomie. Złożony workflow z auto-triggerem i skryptami = skill wielo-plikowy. Pod spodem to ten sam mechanizm - oba tworzą /x.
Narzędzia

CLI, MCP i skill - kryteria wyboru

  • CLI: gdy narzędzie jest dostępne w powłoce, ma stabilne wyjście i łatwo je przetestować.

Nowe trendy

Skills przez MCP i WebMCP

Skills przez MCP

  • Serwer MCP udostępnia skille, agent pobiera je na żądanie.
  • Zawsze aktualna wersja, bez ręcznej aktualizacji w każdym repozytorium.
  • Standard od 13.09.2026 (SEP-2640); klienci dopiero go wdrażają.

WebMCP

  • Strona sama deklaruje narzędzia dla agenta: formularz HTML albo navigator.modelContext.registerTool().
  • Kilka wywołań narzędzi zamiast klikania i czytania DOM: szybciej, taniej, pewniej.
  • Chrome 149: origin trial, lokalnie flaga chrome://flags/#enable-webmcp-testing (dokumentacja).

Przykład WebMCP: Stack Underflow, gra z OpenAI WebMCP Challenge, w której agent przeglądarki gra jako współpracownik w biurze (zagraj).

Moduł 2.4 / TDD

TDD z agentem: Red-Green-Refactor

Cykl TDD

1
Red: test ujawnia brak zachowania.
2
Green: najmniejsza zmiana daje zielony test.
3
Refactor: popraw kod bez zmiany zachowania.

Sprawdź z agentem

  • Test sprawdza wynik, nie sposób implementacji.
  • Uruchom test po każdym kroku.
  • Przed zmianą upewnij się, że test potrafi wykryć błąd.
Moduł 2.4 / wymóg

Małe commity po sprawdzonych zmianach

Dobra historia

  • Jeden spójny, sprawdzony fragment na commit.
  • Test i kod mogą trafić do tego samego działającego commitu.

Unikaj

  • Jednego commitu ze wszystkim na koniec.
  • Łączenia niezależnych zmian.
  • Commitu bez uruchomionych testów.
Test ręczny

Agent przechodzi przez rzeczywisty przepływ

  • Agent otwiera stronę lub CLI i wykonuje scenariusz jak użytkownik - sprawdza stan pusty, błąd i poprawne zgłoszenie.
  • Jeśli jest UI: agent zbiera zrzut, dane z DOM, wynik nawigacji klawiaturą i komunikaty.
  • Porównuje zachowanie z wymaganiami; rozbieżności zapisuje z krokami odtworzenia.
  • Integracje płatne lub zewnętrzne testuj tylko w kontrolowanym środowisku.
3.2 - automatyzacja

Testy E2E jako skill

Agent może pisać i uruchamiać testy Playwright jako dedykowaną umiejętność (skill). To oznacza, że ma zdefiniowane procedury, narzędzia i wzorce.

# Agent generuje test E2E > Napisz test Playwright dla scenariusza: > użytkownik rejestruje się, loguje, > wysyła wiadomość i widzi odpowiedź
# Agent tworzy plik testu i uruchamia: npx playwright test e2e/chat-flow.spec.ts
Zalety
  • Powtarzalne - można uruchamiać w CI/CD
  • Szybkie - sekundy do minut
  • Automatyczne - bez nadzoru człowieka
Ograniczenia
  • Testują tylko to co zaplanowano - nie wykryją niespodziewanych zachowań
  • Kruche - zmiana selektora CSS łamie test
  • Nie zastąpią testów manualnych ("czy to wygląda dobrze?")
3.2 - strategia testów

Mocki zależą od poziomu testu

Dobieraj izolację do celu testu.

Strategia repozytorium rozróżnia trzy poziomy:

  • Unit: mockuj wszystkie zależności
  • Integracja: mockuj tylko zewnętrzny LLM
  • E2E i manualne: nie używaj mocków; testuj realny stos
  • E2E: prawdziwe wywołania modelu
  • E2E: prawdziwa przeglądarka (Chrome/Chromium przez MCP)
  • E2E: prawdziwe API, baza danych i odpowiedzi
Dlaczego to ma znaczenie: szybkie testy jednostkowe izolują logikę, a E2E wyłapuje problemy integracji i rzeczywiste zachowanie modelu. Oba poziomy są potrzebne.
3.2 - narzędzia

Playwright MCP i Chrome DevTools

Playwright MCP

  • Agent steruje przeglądarką przez Model Context Protocol
  • Może nawigować, klikać, wpisywać tekst, robić zrzuty ekranu
  • Weryfikuje czy elementy są widoczne, czy tekst się wyświetla
  • Testuje realne przepływy użytkownika krok po kroku
claude mcp add playwright -s project -- npx @playwright/mcp@latest # konfiguracja projektu ląduje w .mcp.json

Chrome DevTools MCP

  • Agent inspectuje DOM, konsolę, network requests
  • Może weryfikować czy nie ma błędów JavaScript
  • Sprawdza status kodów HTTP w network tab
  • Analizuje wydajność i czasy ładowania
Obie ścieżki sterują prawdziwym silnikiem przeglądarki. Tryb może być headless lub headed; wiarygodność testu nie zależy od widocznego okna.
Interfejs / pełny prompt

Odtworzenie systemu wizualnego

Skopiuj prompt poniżej lub otwórz plik Markdown albo bibliotekę promptów.

System projektowy

Use a real browser automation tool available in this environment to inspect **one public reference page chosen by the learner** and document a reusable design system for a course UI. Do not assume a particular plugin name; first identify the actual browser surface and permissions.

Capture a desktop and mobile screenshot of the chosen page. Inspect visible DOM and computed styles for the header, navigation, one primary action, one form field, a card/list item and the footer. Record concrete design tokens: colors (hex), type families/sizes/weights/line heights, spacing, border radius, borders, shadows and responsive breakpoints. Distinguish measured values from approximations. Record keyboard focus, contrast and error-state behavior where visible. Avoid inventing hidden components from a single screenshot.

Save `assets/design-tokens.json` with a compact set of semantic tokens and `docs/design-guidelines.md` with component patterns, screenshots, responsive notes, accessibility observations and source URL/date. Explain how a frontend developer should apply the tokens to the course app without copying protected brand assets or claiming affiliation with the reference site. If an asset cannot be reused, describe its visual role and provide a neutral substitute. Keep the output actionable: show at least one button, input and card specification and a small verification checklist for comparing the resulting UI in a browser.

Before finishing, reopen the generated files, check token values against the captured evidence and identify any unresolved visual assumptions. Do not implement the application in the same task.
Kontrakt na granicy

Test schematu nie zastępuje testu reguły

  • Jeżeli dwa moduły wymieniają dane, spisz kształt wiadomości i dopuszczalne błędy.
  • Test kontraktowy wykrywa brak pola, zmianę typu i null w wymaganym polu.
  • Test reguły osobno sprawdza poprawność decyzji biznesowej.
  • Nie zmieniaj kontraktu pod przypadkową implementację.

Przykład: wynik funkcji klasyfikującej zgłoszenie (classify_ticket) albo odpowiedź API.

Jakość

Cztery poziomy, cztery pytania

  • Jednostkowy: czy reguła działa na wartościach granicznych?
  • Kontraktowy: czy wejście i wyjście spełniają uzgodniony schemat?
  • Integracyjny: czy dwa moduły współpracują na danych testowych?
  • Przepływ użytkownika: czy zadanie od początku do końca działa?

Liczba testów nie mierzy ryzyka. Test metody wewnętrznej może być zielony, gdy zachowanie jest błędne.

1.3 / path-based rules

Reguła tylko dla frontendu

---
paths:
  - "app/components/**/*.tsx"
---
Zachowaj etykiety formularza i obsługę klawiatury.
Testuj stany wysyłania, błędu i strumieniowania.

Przykład zapisz w .claude/rules/frontend.md i dopasuj ścieżkę do struktury ustalonej w ADR. paths ogranicza ładowanie instrukcji, nie prawa dostępu do plików. Nested CLAUDE.md przechowuje lokalne konwencje; @AGENTS.md importuje wspólne zasady.
