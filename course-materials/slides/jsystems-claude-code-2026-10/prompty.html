Plan i macierz zależności dla aplikacji z PRD

Wskaż aktualny PRD, ADR-y i zakres zadania. Agent przygotuje plan oraz macierz zależności bez rozpoczynania implementacji.

Slajd: Implementacja aplikacji · Pobierz Markdown

# Plan pracy nad aplikacją na podstawie PRD

Pracuję nad projektem opisanym w aktualnym PRD. Zapytaj mnie o ścieżkę do PRD i istniejących ADR-ów, jeśli ich nie podałem. Źródłem wymagań jest **aktualny PRD mojego projektu**, nie przykładowy prompt z materiałów kursowych. Jeśli pracuję nad grupową aplikacją AI Chat z backendem TypeScript, streamingiem i React useChat, pomiń funkcje opcjonalne usunięte z PRD podczas zajęć.

Najpierw ustal stan faktyczny. Przeczytaj wskazany przeze mnie PRD, istniejące ADR-y, wytyczne projektu, README i bieżący kod. Wskaż pliki, które rzeczywiście udało Ci się otworzyć, oraz polecenia uruchomienia i testów, które da się potwierdzić. Katalog `course-materials/` zawiera materiały dydaktyczne i przykłady; nie przeszukuj go ani nie traktuj jego PRD/ADR jako dokumentacji aplikacji, chyba że wskażę konkretny plik. Nie zakładaj, że projekt już działa ani że każdy uczestnik ma ten sam stan repozytorium.

Jeśli wybór bibliotek, architektury lub sposobu uruchomienia nie został jeszcze rozstrzygnięty, wypisz potrzebne decyzje. Sprawdź aktualną dokumentację oficjalną z datą lub wersją, porównaj rozsądne opcje i zaproponuj użycie zainstalowanej umiejętności `write-adr`. Oddziel fakty potwierdzone od założeń. Dla niezależnych decyzji zaproponuj oddzielne ADR-y; nie wymyślaj ich treści przed moją decyzją.

Przygotuj **plan, bez implementowania go teraz**. Podczas warsztatu chcemy przejść cały proces na jednym niewielkim fragmencie, bez obietnicy ukończenia całej aplikacji. Pokaż, jak użyłbyś trybu Plan, i czym różni się plan zapisany w zwykłej sesji: co możesz tam tylko opisać, a co wymaga mojej zgody przed edycją. Jeśli brakuje kluczowych danych, zadaj najpierw kilka konkretnych pytań zamiast zgadywać.

Zwróć:
1. Jednozdaniowy cel najbliższego fragmentu z PRD, zakres poza zadaniem i kryteria akceptacji możliwe do sprawdzenia.
2. Fazy: rozpoznanie stanu → ewentualne ADR → plan → test, który początkowo nie przechodzi → niewielka implementacja → testy i kontrola ręczna w przeglądarce, jeśli jest UI → pokaz grupie → poprawka rzeczywistego problemu → niezależny przegląd → pull request tylko dla gotowego fragmentu.
3. **Macierz zadań i zależności**. Dla każdego wiersza podaj: identyfikator, wynik, zależności, właściciela, pliki lub obszar własności, kryterium ukończenia, test albo inny dowód, punkt kontroli człowieka i możliwy następny krok. Oznacz, co da się robić równolegle, a co trzeba wykonać po kolei.
4. Propozycję delegowania wyłącznie niezależnych zadań. Porównaj jednego agenta z subagentami domyślnymi, doraźnymi i własnymi; domyślnie wybierz subagentów doraźnych do jednorazowych zadań, a krótkie definicje własne tylko dla powracających ról i ograniczeń narzędzi. Brief wykonawcy przygotuj tuż przed zatwierdzonym uruchomieniem, z aktualnymi kontraktami i rozłącznymi plikami. Nie zakładaj, że wszystkie rodzaje subagentów są dostępne w używanej wersji Claude Code. Poinformuj każdego wykonawcę o równoległej pracy. Zmiany wspólnych plików wykonuj kolejno. Nie twórz worktree na każdą sesję; poproś o zgodę tylko przy konkretnej potrzebie izolacji. Do ograniczonych prac nad kodem i testami preferuj Claude Haiku. Sprawdź dostępność modelu i uprawnienia w bieżącej sesji. Decyzje i odbiór należą do mocnego orkiestratora.
5. Jeden wspólny sposób śledzenia stanu pracy w zespole (np. GitHub Issues, Jira, Linear albo Beads, jeśli już go używamy). Nie twórz równoległych źródeł prawdy bez potrzeby. Pokaż przekazanie zadania między agentami i sposób scalenia wyników przed testami całości.
6. Plan kontroli jakości: testy lokalne, kontrola działania aplikacji przez agenta i człowieka, przegląd zmian, reakcja na uwagi z code review, dokumentacja wyników. Oddziel wynik faktycznie sprawdzony od deklaracji agenta.
7. Plan awaryjny, jeśli zabraknie czasu, dostępu, przeglądarki lub kredytów AI: najmniejszy pokaz możliwy do wykonania z istniejącym kodem i jasny zapis pracy do dokończenia.

Zapisz szkic planu w `docs/plans/<funkcja>-plan.md`, chyba że wskażę inne miejsce. W trybie Plan bez prawa zapisu najpierw zwróć szkic i proponowaną ścieżkę. Odsyłaj do konkretnych kryteriów PRD i sekcji ADR, zamiast powielać ich treść. Poza tym dokumentem nie modyfikuj plików; nie implementuj funkcji, nie twórz gałęzi, issue ani pull requesta i nie uruchamiaj delegowanych agentów, dopóki nie przejrzę planu. Nie narzucaj z góry konkretnego języka, frameworka, liczby agentów ani nazw plików, których nie ma w projekcie. Na końcu wskaż trzy najważniejsze decyzje, które mam zatwierdzić przed rozpoczęciem pracy.


Po omówieniu planu przeprowadź ćwiczenie: wspólnie wydzielimy procedurę planowania do własnego `SKILL.md`, bez domeny aplikacji i nazw klienta. Skill ma zawierać wyzwalacz, wejścia, macierz zależności, granice plików, dobór modeli i zatrzymanie przed implementacją. Sprawdzimy go na drugiej małej funkcji. Opcjonalne porównanie: [publiczna propozycja write-implementation-plan, PR #28](https://github.com/EdukeyTeam/agent-toolbox/pull/28), oczekuje na przegląd; nie jest wymaganą zależnością.


Kontekst AI Chat: kontrakt endpointu i streamingu ustalamy przed równoległą pracą. Role to `be-developer`, `fe-developer` oraz `qa-engineer`; uczestnik definiuje je w module 2.3. Przykłady w `course-materials/agent-configs/claude/` są nieaktywne. Podaj właściciela wspólnego kontraktu i lockfile. QA może przygotować scenariusze równolegle, lecz E2E uruchamia po integracji. Nie zakładaj istniejącej autoryzacji ani bazy historii, jeśli PRD ich nie wymaga.

01

PRD aplikacji AI Chat

Przykład PRD dla syntetycznego projektu. Przed użyciem dostosuj opis i dane wejściowe do własnej aplikacji.

Slajd: Implementacja aplikacji · Pobierz Markdown

Użyj zainstalowanego publicznego skilla `write-prd`, aby przygotować `docs/PRD.md` dla aplikacji **AI Chat**. To aplikacja budowana od pustego szkieletu na trzydniowym warsztacie. Skill prowadzi rozmowę o wymaganiach i sposób zapisu dokumentu; poniższe informacje są pełnym kontekstem produktu, a nie gotową specyfikacją architektury. Nie implementuj teraz aplikacji i nie zastępuj rozmowy o brakujących wymaganiach własnymi założeniami.

## Problem i użytkownik

Użytkownik chce prowadzić rozmowę z modelem AI w prostej aplikacji webowej. Nie chce czekać na całą odpowiedź bez informacji o postępie ani tracić wpisanego tekstu, gdy dostawca zwróci błąd. Potrzebuje czytelnej historii bieżącej rozmowy, rozróżnienia wiadomości użytkownika i modelu oraz jasnego stanu wysyłania, generowania i błędu. Interfejs ma działać na komputerze i telefonie. Używamy wyłącznie danych syntetycznych i krótkich, nieszkodliwych pytań testowych.

Główny użytkownik wpisuje wiadomość, wysyła ją i widzi stopniowo dopisywaną odpowiedź. Druga persona to osoba rozwijająca aplikację: musi móc odtworzyć błąd, sprawdzić kontrakt i uruchomić testy bez ujawniania poświadczeń. Rozdziel jej potrzeby od funkcji samego czatu. Określ, po czym poznamy, że pierwszy przepływ jest gotowy, zamiast mierzyć sukces liczbą wygenerowanych plików.

## Przepływy i zachowanie do uzgodnienia

- Rozpoczęcie nowej rozmowy: pusty widok ma objaśniać następny krok, mieć etykietę pola wiadomości i przycisk wysłania. Ustal z uczestnikiem przykładowe teksty po polsku i dostępność klawiaturą.
- Wysłanie wiadomości: walidujemy pusty tekst oraz białe znaki. Przed implementacją uzgodnij granicę długości wiadomości i sposób pokazania błędu. Nie wymyślaj arbitralnego limitu.
- Streaming: po wysłaniu użytkownik widzi swoją wiadomość, stan pracy i przyrost odpowiedzi. Ustal zachowanie przy drugiej próbie wysłania podczas generowania. Nie akceptuj jedynie animacji udającej strumień gotowej odpowiedzi.
- Kontynuacja: kolejne pytanie korzysta z kontekstu bieżącej rozmowy. Uzgodnij, jak duża historia jest przekazywana i jak użytkownik zaczyna nową rozmowę. Nie dodawaj automatycznie bazy danych.
- Błąd dostawcy lub sieci: czytelny komunikat, zachowany wpisany tekst i możliwość świadomej ponownej próby. Nie pokazuj klucza, surowego stack trace ani pełnych poufnych żądań.
- Przerwanie odpowiedzi i ponawianie: zapytaj, czy należą do pierwszego zakresu. Jeśli tak, opisz widoczny stan częściowej odpowiedzi i warunki ponowienia. Nie zakładaj takiego samego zachowania dla przerwania i awarii.
- Odpowiedź zawierająca kod lub Markdown: uzgodnij, czy pierwsza wersja wyświetla tekst, czy bezpiecznie renderuje Markdown. Surowy HTML i skrypty z modelu nie mogą wykonywać się w przeglądarce.

Techniczne ramy szkolenia to TypeScript, backend i frontend, streaming oraz Vercel AI SDK z React `useChat`. W PRD zapisz je jako znane ograniczenia, lecz wybór Next.js albo Vite z osobnym API, dostawcy i wersji SDK zostaw do ADR. Klucz modelu pozostaje po stronie serwera. Subskrypcja do pracy z Claude Code nie jest automatycznie kluczem API do budowanej aplikacji.

## Zakres pierwszej wersji i dowody

Zaproponuj najmniejszą spójną wersję: jedna rozmowa w bieżącej sesji, wiadomości tekstowe, prawdziwy streaming, obsługa błędu i czytelny interfejs. Poza tym zakresem pozostają płatności, konta użytkowników, RAG, upload plików, narzędzia wykonywane przez model i trwała historia, chyba że świadomie zmienimy zakres. Historia wielu rozmów i Markdown mogą być rozszerzeniem po działającym minimum.

Przygotuj co najmniej cztery przypadki demonstracyjne: poprawna wiadomość z przyrostem tekstu, kontynuacja rozmowy, pusty input oraz awaria usługi. Dla każdego zapisz widoczny wynik i numerowane kryteria akceptacji, z których tester może wyprowadzić uczciwy test. Dodaj mapowanie kryterium -> scenariusz -> dowód. Nie wymagaj dokładnego brzmienia odpowiedzi probabilistycznego modelu; sprawdzamy zachowanie aplikacji i kontrakt.

Najpierw przeczytaj instrukcje repozytorium i rzeczywisty stan szkieletu. Zadawaj tylko pytania, których odpowiedzi brakuje i które zmieniają zachowanie produktu. Oddziel ustalone fakty od propozycji i otwartych pytań. Po rozmowie zapisz dokument według skilla, pokaż zakres do przeglądu i zakończ. Implementacja, delegowanie oraz tworzenie gałęzi nie należą do tego zadania.

ADR architektury AI Chat

Przykład ADR dla syntetycznego projektu. Przed użyciem wskaż aktualny PRD i decyzję architektoniczną.

Slajd: Implementacja aplikacji · Pobierz Markdown

Użyj zainstalowanego publicznego skilla `write-adr`, aby opisać architekturę **AI Chat** z aktualnego `docs/PRD.md`. Przeczytaj cały PRD, instrukcje repozytorium i istniejący szkielet. Zastosuj sposób pracy skilla, a dokumenty zapisz w `docs/ADR/`. Nie implementuj kodu. Zachowanie produktu wynika z PRD; ADR ustala techniczne decyzje i ich konsekwencje.

To greenfield w TypeScripcie na przygotowanej VM Ubuntu Linux (8 GB RAM, 4 rdzenie). Wspólne ramy kursu to Vercel AI SDK po stronie serwera, React z `useChat` i rzeczywiste strumieniowanie odpowiedzi. Porównaj dwa sensowne warianty: Next.js z endpointem w tej samej aplikacji oraz Vite + React z osobnym API Hono albo Express. Nie wybieraj stosu tylko dlatego, że występuje w historycznym przykładzie. Nie wprowadzaj Docker ani bazy, jeśli PRD ich nie potrzebuje.

## Biblioteki i źródła do porównania

- Vercel AI SDK: https://ai-sdk.dev/docs/introduction i przewodnik streamingu https://ai-sdk.dev/docs/ai-sdk-ui/chatbot . Zweryfikowany Context7 ID: `/websites/ai-sdk_dev`.
- AI SDK UI i React `useChat`: https://ai-sdk.dev/docs/reference/ai-sdk-ui/use-chat . Ustal aktualne importy, sposób wysyłania i strukturę wiadomości zamiast kopiować nieaktualny interfejs `ai/react`.
- Anthropic provider: https://ai-sdk.dev/providers/ai-sdk-providers/anthropic oraz oficjalne dokumenty API https://platform.claude.com/docs/ .
- OpenRouter provider: https://openrouter.ai/docs/community/vercel-ai-sdk i https://openrouter.ai/docs/ . Sprawdź dostępność modelu, obsługę streamingu, limity i trasę danych.
- Next.js: https://nextjs.org/docs .
- Vite: https://vite.dev/guide/ ; Hono: https://hono.dev/docs/ ; Express: https://expressjs.com/ .
- Playwright: https://playwright.dev/docs/intro .

Agent pobiera aktualną dokumentację przez Context7 lub z oficjalnych stron, porównuje opcje i podaje źródła z datą oraz wersjami. Uczestnik ocenia dowody i zatwierdza wybór. Nie zakładaj, że dostęp do Claude Code zapewnia środki na API aplikacji; sposób uwierzytelniania i model ustalamy osobno, bez odczytu wartości sekretów.

## Decyzje wymagające uzasadnienia

- Granica UI/API: odpowiedzialność za walidację, limit wiadomości z PRD, format żądania, model błędu oraz reprezentacja historii rozmowy. Nie narzucaj nieuzgodnionego limitu.
- Kontrakt streamingu: jak backend zamienia wiadomości UI na wiadomości modelu, jak wysyła strumień zgodny z używaną wersją AI SDK UI i jak frontend składa części odpowiedzi. Uwzględnij anulowanie, zamknięcie połączenia, timeout i niepełną odpowiedź.
- Dostawca: porównaj Anthropic i OpenRouter pod kątem potrzeb PRD, zgodności protokołu, dostępu, kosztów i ograniczeń danych. Zapisz nazwę wybranego modelu i wersję biblioteki dopiero po sprawdzeniu źródła.
- Stan rozmowy: czy wystarcza pamięć bieżącej sesji, co dzieje się po odświeżeniu i jaki zakres kontekstu wraca do modelu. Jeżeli trwała historia jest poza PRD, odłóż bazę danych i migracje.
- Sekrety i logi: klucz wyłącznie na serwerze, nazwy w `.env.example`, bez wartości w kodzie klienta, logach, screenshotach i Git. Przedstaw czytelny błąd dla braku konfiguracji.
- Bezpieczny rendering: tekst albo Markdown według PRD; treść modelu jest niezaufana, surowy HTML nie może wykonywać kodu. Opisz dostępność pola, przycisku i stanu generowania.
- Podział pracy: kontrakt i manifest zależności mają właściciela; `be-developer` i `fe-developer` dostają rozłączne obszary, a `qa-engineer` przygotowuje scenariusze i uruchamia E2E po integracji.

Dla każdego istotnego wyboru podaj realistyczną alternatywę, powód odrzucenia, konsekwencje i warunek ponownej oceny. Diagram komponentów i sekwencji ma objąć wysłanie wiadomości, przyrost strumienia, kontynuację i awarię. Opisz kontrakty, modele danych na poziomie pojęć oraz strategię testów powiązaną z kryteriami PRD. Oddziel testy jednostkowe, integracyjne i E2E. Integracyjne mogą zastąpić zewnętrzny model; E2E obejmuje prawdziwy stos i ograniczoną liczbę rzeczywistych żądań. Mock kontraktu powstaje z bezpiecznego, świeżego capture, nie z domysłu.

Zweryfikuj polecenia startu i testów w wybranym szkielecie, zanim wpiszesz je jako działające. Jeśli szkielet jeszcze nie istnieje, oznacz tę zależność i zaplanuj weryfikację po jego utworzeniu. Zachowaj źródła i wersje tak, aby następny agent mógł ponownie pobrać dokumentację. Niezależne decyzje rozdziel na odpowiednie ADR-y zgodnie ze skillem. Zakończ listą decyzji do zatwierdzenia, bez scaffoldingu i bez uruchamiania subagentów.

Najpierw opisz faktyczną strukturę repozytorium i sprawdzone polecenia. Wskaż, które dokumenty zawierają wymagania produktu, decyzje architektoniczne, polityki, testy i syntetyczne dane. Rozróżnij dokumenty już istniejące od wyników przyszłych ćwiczeń. Wskaż katalogi generowane, sekrety i dane, które nie mogą trafić do Git. Jeśli polecenie nie działa w tym środowisku, przytocz dokładny błąd i nie przedstawiaj go jako sprawdzonego.

Zaproponuj krótkie instrukcje obejmujące:

Oceń dowody. Przeczytaj asercje, nie tylko nazwy testów. Ustal, czy nowy test potrafił wykryć brakujące zachowanie przed implementacją, co jest mockowane i czy E2E uruchomiono na rzeczywistym stosie. Oddziel build, testy, start aplikacji i QA. Nie akceptuj raportu mówiącego wyłącznie "wszystko działa". Jeśli nie możesz odtworzyć testu, opisz ograniczenie i dokładny brakujący warunek.

Dla każdego potwierdzonego problemu podaj istotność, plik i linię, konkretny scenariusz wejściowy, wpływ na użytkownika, dowód oraz najmniejszą propozycję naprawy z testem regresji. Oddziel błędy blokujące od sugestii i pytań. Jeśli brak problemów, wskaż sprawdzony zakres i pozostające ryzyka; nie wymyślaj uwag dla samej liczby.

Uwierzytelnianie API i OAuth to osobne konfiguracje, nie wymagaj obu. Nie uruchamiaj kodu z niezaufanego PR z uprawnieniami do sekretów. Ustal limit tur i budżetu.
