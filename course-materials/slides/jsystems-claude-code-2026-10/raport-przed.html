Wniosek przewodni

Zespół nie potrzebuje kolejnego przeglądu narzędzi AI. Największą wartość da wspólny, powtarzalny standard pracy: od kontekstu i specyfikacji, przez plan i implementację, po testy, wieloagentowy przegląd i akceptację człowieka.

Największe ryzyko organizacyjne

W tym dwudniowym kursie dostęp administracyjny oraz instalacja Dockera, IDE i Claude Code wymagały sprawdzenia przed szkoleniem. Dla nowej grupy plan środowiska wynika z jej własnego stosu i uprawnień.

Rzeczywisty kontekst techniczny

  • 01
    Dwa światy systemoweStarsze rozwiązania legacy oraz nowsze produkty oparte na wielu usługach i repozytoriach.
  • 02
    Architektura rozproszonaWarstwa API/gateway, wiele usług backendowych i repozytoriów oraz rozwiązania w więcej niż jednym języku.
  • 03
    Kontekst jest rozproszonyPRD i dokumentacja biznesowa w Confluence, zadania w Jira, Swagger i szczegóły techniczne w repozytoriach Bitbucket.

    Backend-firstVue istnieje w stosie, ale główną potrzebą są przepływy backendowe, debugowanie, optymalizacja i praca między usługami.
  • 05
    Duży potencjał w automatyzacji jakościW poprzednim zespole pipeline zawierał głównie healthcheck (HTTP 200), a testów automatycznych praktycznie nie było. Test-first, kryteria akceptacji i automatyczne bramki jakości stały się priorytetem.
  • 06
    Wspólny agent, różny poziom praktykiW poprzednim kursie Claude Code było dostępne, lecz doświadczenie zespołu rozciągało się od podstaw do zaawansowanych workflow.

04 · Przykład decyzji programowych

Jeden przepływ end-to-end

1
PRDAnaliza dokumentacji, wywiad, Q&A, persony, przepływy, założenia nietechniczne od strony użytkownika.
2
ADRResearch techniczny na podstawie PRD; decyzje zapisane w ADR z uzasadnieniem.
3
PlanSzczegółowy opis zadań dla agentów: zależności (dependency matrix), przypisanie do subagentów, decyzja co równoległe a co blokujące, wbudowane kroki QA.
4
AkceptacjaSprawdzenie planu przez człowieka przed realizacją; poprawki.
5
Wdrożenie z TDDNajpierw testy (fail), potem wdrożenie i pass; oddelegowane do subagentów.
6
QA z AIGłówny agent koordynuje i kontroluje jakość przez cały czas wdrożenia: code review, akceptacja, poprawki.
7
Końcowe QAKońcowe lokalne code review przez AI i człowieka, debugging i poprawki; testy E2E i "manualne" wykonywane przez AI.
8
CI/CDPR, testy, analiza statyczna i AI Code Review w chmurze, poprawki.

05 · Środowisko poprzedniej grupy

Jedna ścieżka dla całej grupy

rekomendowane

Własne stacje robocze

Największa szansa, że wypracowany sposób pracy zostanie z zespołem po szkoleniu. Do sprawdzenia, czy każdy może zainstalować:

  • Windows + Docker Desktop z backendem WSL2
  • Obrazy testowe uruchamiane wspólnie na początku kursu
  • Git for Windows
  • Node.js LTS - dla narzędzi agentowych/MCP opartych na npm lub npx oraz awaryjnej pracy z frontendem
  • Claude Code CLI zainstalowany natywnie w Windows
  • IDE zgodne ze stosem poprzedniej grupy
  • Testowa organizacja Bitbucket z repozytorium
LUB
fallback

Maszyny VM - dla wszystkich

W poprzednim planie VM stanowiły wspólną ścieżkę awaryjną, z przygotowanym środowiskiem i połączeniem przez Pulpit Zdalny Windows. Grupa nie dzieli się - albo VM dla wszystkich, albo dla nikogo.

  • Wszystko zainstalowane i sprawdzone (IDE, oprogramowanie)
  • Dostępne do 17:00 w dniach kursu
  • Uczestnicy muszą odtwarzyć środowisko na swoich maszynach po kursie

Dlaczego laptopy wygrywają

Uczestnicy uczą się w środowisku, którego będą używać później. To usuwa dodatkowy krok migracji z jednorazowej maszyny i zwiększa szansę wdrożenia praktyk po kursie.

Warunek powodzenia

W poprzednim kursie uczestnicy sprawdzali instalację Dockera i Claude Code przed szkoleniem. Repozytorium oraz obrazy aplikacji uruchamiano wspólnie na początku warsztatu.

06 · Przykładowe rekomendacje z poprzedniego kursu

Co ustalono przed tamtym szkoleniem

1. Potwierdzić politykę instalacji i AI

Ustalić prawa administratora, możliwość użycia WSL2/Dockera/Claude Code oraz zasady przekazywania kodu i dokumentacji do modelu. To blokuje wybór środowiska i zakres realnych przykładów.

2. Wybrać ścieżkę środowiskową - dla całej grupy

W poprzednim planie wybrano jedną ścieżkę dla całej grupy: własne laptopy albo VM. Weryfikacja obejmowała Docker Desktop z Compose i backendem WSL2, Git for Windows, Node.js LTS, Claude Code CLI oraz IDE odpowiednie dla stosu. Osobna dystrybucja Ubuntu w WSL2 pozostawała opcjonalna. Obrazy testowe i repozytorium uruchamiano wspólnie na początku kursu.

3. Rozesłać instrukcję instalacji i weryfikację

Dla poprzedniej grupy przygotowano listę wersji narzędzi i krótką kontrolę działania środowiska. Osobno sprawdzono backend WSL2 i czas na pomoc zespołu IT. Dostęp do repozytorium kursu oraz obrazy aplikacji uruchomiono razem na początku szkolenia.

4. Otrzymać zanonimizowane artefakty

Przykład PRD/specyfikacji, ADR, fragment OpenAPI/Swagger, mapa usług, przykładowy pipeline i obecna checklista testów - bez danych klientów, sekretów i kodu produkcyjnego.

5. Uzgodnić jeden syntetyczny przypadek

Dla poprzedniego kursu wybrano uproszczony, całkowicie syntetyczny proces bliski pracy uczestników: warstwę API i 1-2 usługi, z rolami, audytem i błędami do diagnozy.

6. Przygotować dwie ścieżki ćwiczeń

Nowa funkcja w usługach oraz diagnostyka/refactoring legacy z testami charakteryzacyjnymi. Wspólny standard, inne punkty wejścia.

7. Dostarczyć pre-work

Krótki słownik pojęć, zasady kontekstu i bezpieczeństwa oraz 20-30 minut obowiązkowego przygotowania. Teoria nie powinna zabierać czasu na szkoleniu.

8. Dostarczyć instrukcje instalacji i testowe repozytorium

Osobny plik z wersjami narzędzi oraz dostęp do testowego repozytorium na platformie używanej przez poprzednią grupę.

07 · Przykładowe pytania do potwierdzenia

Informacje potrzebne do finalizacji

Instalacja i sprzęt

Czy uczestnicy mogą zainstalować wymagane narzędzia i IDE? Czy mają lokalne uprawnienia administratora, odpowiedni sprzęt oraz działającą wirtualizację, jeśli ćwiczenia jej wymagają? Czy wszyscy mogą pracować w tej samej ścieżce środowiskowej?

Sieć i dostęp

Czy proxy, VPN, EDR lub firewall ograniczają pobieranie zależności, logowanie do narzędzia AI albo klonowanie repozytorium warsztatowego?

Wersje stosu

Jakie języki, frameworki i wersje narzędzi będą używane w ćwiczeniach? Jak lokalnie uruchomić przykładową aplikację i jej zależności?

Dokumentacja i przykład

Czy możecie przesłać zanonimizowane szablony PRD/specyfikacji, ADR, fragment kontraktu API, uproszczoną mapę zależności oraz jeden proces lub ticket, który może zainspirować ćwiczenie?

Testy i krytyczne funkcjonalności

Jakie testy i bramki jakości ma dziś zespół? Które funkcjonalności są krytyczne i wymagają pokrycia jednostkowego, integracyjnego lub E2E? Co jest testowane manualnie i mogłoby zostać zautomatyzowane?

Zakres architektury

Które 1-2 usługi oraz fragment warstwy API najlepiej reprezentują typowe zależności, bez odwzorowywania całego środowiska? Które narzędzia pomocnicze są tylko kontekstem, a które mają być aktywnym tematem?

Organizacja grupy

Ilu uczestników weźmie udział w kursie, a ilu odpowiedziało na ankietę? Jakie są ich role i poziomy doświadczenia? Czy konta oraz licencje do narzędzi szkoleniowych będą aktywne przed rozpoczęciem?

Efekt po szkoleniu

Które artefakty mają największy priorytet: instrukcje repozytorium, szablon specyfikacji/ADR, role agentów, zasady MCP, checklisty testów/review czy przykład pipeline?

Zakres danych do bezpiecznego udostępnienia

Materiały szczególnie pomocne
  • zanonimizowany PRD lub specyfikacja;
  • przykładowy ADR i fragment OpenAPI/Swagger;
  • uproszczona mapa monolitu, gateway i usług;
  • zanonimizowany ticket/problem utrzymaniowy;
  • syntetyczna lub oczyszczona konfiguracja pipeline CI;
  • obecna checklista manualnego testowania i code review.
Czego nie przesyłać
  • danych klientów, dostawców ani użytkowników;
  • sekretów, tokenów, kluczy, adresów wewnętrznych i konfiguracji produkcyjnej;
  • pełnych repozytoriów lub dokumentów bez wcześniejszej anonimizacji;
  • logów zawierających dane osobowe lub informacje poufne.
Metodologia i prywatność. Ten przykład zachowuje zagregowane wyniki ankiety z rzeczywistego kursu (9 zgłoszeń, 8 unikalnych osób po scaleniu duplikatu) oraz zanonimizowane wnioski ze spotkania discovery. Przed publikacją dla nowej grupy trzeba zastąpić wyniki i wnioski jej własnymi danymi. Nie zawiera nazwisk, odpowiedzi indywidualnych, danych kontaktowych, kodu, dokumentów ani szczegółów pozwalających odtworzyć środowisko produkcyjne. Strona ma ustawienie noindex.
